# Networking

Media and input go **peer-to-peer** (WebRTC). The signaling server only exchanges offers/answers and issues STUN/TURN info.

| Situation | What happens |
|---|---|
| Both behind ordinary home/office NAT | STUN finds public addresses → direct connection |
| Symmetric NAT / CGNAT (many mobile carriers), strict corporate firewalls (UDP blocked) | direct fails → **TURN relay** (coturn). Without TURN these cases cannot connect. |

Recommended cost-conscious setup: one small VPS running `signaling/deploy/docker-compose.yml` (Caddy HTTPS + signaling + coturn). TURN credentials are short-lived (1 h, HMAC "REST API" scheme) and generated by the signaling server from `TURN_SECRET`; the secret never leaves the server. coturn denies relaying to private IP ranges. To work through firewalls that block UDP, add `turns:` on 443/5349 with a certificate (see coturn docs) and list it in `TURN_URLS`.
A relayed session uses your VPS bandwidth (~0.5–3 Mbit/s each way while active).

Other facts
- Phone reconnect: if ICE fails/disconnects >6 s the app re-offers automatically (5 tries, backoff). Wi-Fi↔LTE switches normally trigger this.
- Agent reconnects to signaling with exponential backoff (1→60 s) after outages.
- The PC must be on, logged in, not sleeping. Disable sleep or use Windows power settings; Wake-on-LAN is not implemented.
- Corporate networks may forbid outbound WSS/UDP or remote-access tools — check policy before use.
- **Verification status:** the same-machine loopback path is tested end-to-end; STUN/TURN and real cross-network behaviour are implemented but **not verified** in this environment (no public server/second network available).
